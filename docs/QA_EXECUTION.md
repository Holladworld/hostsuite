# HostSuite QA Execution

## Current automated QA status

The repository currently has build, lint and TypeScript checks configured. Automated test files have now been added under `tests/qa/` for billing, security, provider safety, AI safety and payment invariants.

Before declaring the suite green, install a test runner (Vitest is the intended runner), add the corresponding `test` script and commit the lockfile generated by the project's package manager. Do not claim a passing test run until the commands have actually executed successfully in CI or a reproducible local environment.

## Required commands

```bash
npm install
npm run typecheck
npm run lint
npm run build
npm test
```

## Required E2E/security tests before staging

- Customer A cannot read or mutate Customer B data.
- Anonymous users cannot call protected APIs.
- Non-admin users cannot perform admin mutations.
- Invalid Paystack and Flutterwave webhooks are rejected.
- Duplicate payment events are idempotent.
- A client-side success response cannot grant an entitlement by itself.
- AI generation requires authenticated ownership and sufficient credits.
- AI usage is recorded against the correct customer/project.
- Generated code cannot execute in the HostSuite web process.
- Provider failures do not activate services.
- Unsupported provider capabilities fail explicitly.
- Secrets never appear in client bundles or API responses.

## Staging smoke test

After the automated suite is green and feature branches are merged into `staging`, manually verify:

1. Landing page loads.
2. Signup/login/logout/recovery work.
3. Customer onboarding works.
4. Portal navigation works.
5. CMS can update permitted public content without code changes.
6. Pricing is read from configuration rather than hard-coded UI values.
7. Checkout creates the expected order.
8. Verified payment changes the correct entitlement.
9. Failed/duplicate payment does not create duplicate entitlements.
10. AI builder entry point works in configured environments.
11. AI credit balance and usage display correctly.
12. Provider-dependent features show clear setup/unavailable states when credentials are absent.
13. Monitoring/support/automation flows are reachable and understandable.
14. Admin cannot accidentally mutate another tenant's data.
15. Mobile and desktop critical paths are usable.

## Release rule

`staging` is the first integration environment. `main` must remain untouched until the owner explicitly approves promotion after this checklist passes.
